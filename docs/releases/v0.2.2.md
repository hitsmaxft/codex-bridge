# Codex App Server WebUI v0.2.2

This patch release makes voice input capability explicit before recording begins. Bridge status
and WebSocket service snapshots now tell the Web UI whether the connected app-server can perform
realtime speech transcription with its current authentication mode.

## Voice capability handshake

The bridge reads `account/read` with `refreshToken: false` during its ordinary status request. It
derives `capabilities.audio_transcription` from the returned account type and caches:

- `enabled`, the value used by the composer;
- `reason`, such as `api_key_auth_required`; and
- `auth_mode`, such as `apiKey` or `chatgpt`.

Immediate and periodic `bridge_service_snapshot` events include the cached value. Periodic pushes
do not repeat the RPC, trigger token refresh, or open a trial realtime session. An
`account/updated` event makes the Web UI request fresh status once.

## Composer behavior

When server transcription is unavailable, the microphone remains visible but is disabled and
marked with a red cross. Its localized accessible label explains the limitation. API-key and Demo
modes keep the existing record, browser PCM conversion, server transcription, and editable-text
flow.

The mobile composer also stops intercepting pointer-down events across its entire visual shell.
Only the textarea and visible controls receive pointer events; unused padding and spacer regions
pass through to the message view. Queue/Steer and Submit now use native click delivery, avoiding
the iOS failure mode where preventing pointer-down default behavior suppressed the later click.

## Remembered session folders

Expanded project folders are stored as a bounded browser preference. On startup and list refresh,
the Web UI restores valid folders and preloads their lightweight session summaries in the
background with at most three concurrent requests. App-server exposes `name` and `preview` in
`thread/list`, plus summary-only `thread/read(includeTurns: false)`; the expand/collapse choice
itself remains client UI state.

## Historical patch rendering

Some rollout tails contain an `apply_patch` custom-tool input before an agent message ID is
available. In current orchestrated sessions its sole `request` value can be the literal `patch`, an
opaque invocation marker with no diff data; app-server separately exposes the real edit as a
structured `fileChange`. The marker is now omitted from history. Older records that carry a bounded
`*** Begin Patch` envelope are normalized into a rendered diff with file and line summaries.
